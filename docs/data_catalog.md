# Data Dictionary

The Silver and Gold layers are documented in the dbt project
([`data_warehouse/`](../data_warehouse/README.md#documentation)): every model,
snapshot and column has a description, written next to its tests, so the
documentation changes in the same commit as the code. There are three ways to
read it:

- **The dbt documentation site**, with every model, its columns, types, tests
  and SQL, and the lineage graph: from `data_warehouse/`, run
  `dbt docs generate` and `dbt docs serve`.
- **The YAML files** in the repository: `models/silver/_silver__models.yml`,
  `models/gold/_gold__models.yml` and `snapshots/_snapshots.yml`.
- **SQL Server itself**: dbt writes each description as an `MS_Description`
  extended property, visible in SSMS (object Properties → Extended
  Properties) or with this query:

  ```sql
  SELECT OBJECT_SCHEMA_NAME(ep.major_id)  AS schema_name,
         OBJECT_NAME(ep.major_id)         AS object_name,
         c.name                           AS column_name,  -- NULL: the object itself
         CAST(ep.value AS NVARCHAR(4000)) AS description
  FROM sys.extended_properties AS ep
  LEFT JOIN sys.columns AS c
      ON c.object_id = ep.major_id
     AND c.column_id = ep.minor_id
  WHERE ep.name = 'MS_Description'
    AND OBJECT_SCHEMA_NAME(ep.major_id) IN ('silver', 'gold', 'snapshots')
  ORDER BY schema_name, object_name, ep.minor_id;
  ```

This document gives the map of the Gold layer and describes the one table
that dbt does not build: `bronze.load_log`.

# Gold Layer

| Object | Grain | Keys |
|---|---|---|
| `gold.dim_customers` | One row per customer, current state | `customer_key` (hash of `customer_id`) |
| `gold.dim_products` | One row per product, current version | `product_key` (hash of `product_number`) |
| `gold.fact_sales` | One row per product within an order | `customer_key`, `product_key`, `customer_version_key`, `product_version_key` |
| `gold.dim_customers_history` | One row per version of each customer | `customer_version_key`; `customer_key` is the same as in `dim_customers` |
| `gold.dim_products_history` | One row per version of each product | `product_version_key`; `product_key` is the same as in `dim_products` |

## Relationships

```
                  dim_customers (1) ──< (N) fact_sales (N) >── (1) dim_products
     customer_key ──────────── customer_key           product_key ──────────── product_key

          dim_customers_history (1) ──< (N) fact_sales (N) >── (1) dim_products_history
customer_version_key ── customer_version_key        product_version_key ── product_version_key
```

- The durable keys (`customer_key`, `product_key`) join a sale to the
  current customer and product.
- The version keys join it to the version in force on the sale date (the
  order date, or the shipping date when the order date is missing).
- Every key of `fact_sales` is resolved with a `LEFT JOIN`, so a sale whose
  customer or product is missing keeps a `NULL` key instead of being dropped;
  the dbt tests check that no key is `NULL` today.

# Operational Table

## bronze.load_log

Load history. One row per load attempt made by the Python ingestion layer
(`python -m ingestion.main`), whether it succeeded or failed. It is not source
data: nothing in Silver or Gold reads it. Its script,
`scripts/bronze/ddl_load_log.sql`, creates it only if it does not exist and
the table is never truncated, so the history is kept between runs.

| Column | Data Type | Description |
|---|---|---|
| `load_id` | `INT` | Primary key (`PK_load_log`). Sequential number generated by `IDENTITY`, so a higher value is a more recent attempt. |
| `table_name` | `NVARCHAR(257)` | Bronze table that was loaded, as `schema.table` (for example `bronze.crm_cust_info`). |
| `status` | `NVARCHAR(10)` | Outcome of the attempt: `'SUCCESS'` or `'FAILED'` (enforced by `CK_load_log_status`). |
| `rows_loaded` | `INT` | Number of rows loaded. `NULL` when the load failed. |
| `error_message` | `NVARCHAR(2000)` | Error type and message, cut to 2000 characters. `NULL` when the load succeeded. |
| `logged_at` | `DATETIME2(3)` | Moment the row was written. Filled by the database with `SYSDATETIME()` (`DF_load_log_logged_at`). |

Every attempt leaves exactly one row, and a failed load rolls back the table
it was loading, so a `FAILED` row means the previous data is still in place.
